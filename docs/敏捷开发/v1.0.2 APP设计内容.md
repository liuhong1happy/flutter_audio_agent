### 变更:本地向量化的运行时,从 `flutter_onnxruntime` 改为 `flutter_embedder`

- **原设计**用 `flutter_onnxruntime` + `onnxruntime-android` 跑 bge-small-zh-v1.5。
- **实测证伪**:`sherpa_onnx` 自带一份 `libonnxruntime.so`,与该插件依赖的那份
  **同 soname 但符号版本节点不同**(`VERS_1.27.1` vs `VERS_1.23.0`)⇒
  **同一 APK 内不可能共存**。详见 `TODO.md` 坑 19(含两次误判的过程留痕)。
- **改用** `flutter_embedder`(Rust + `ort` crate 的 `load-dynamic`):
  运行时 `dlopen` **sherpa 已在 APK 里的那份 ORT**,因此**不需要**
  `onnxruntime-android`,冲突自然消失。
- 该依赖指向 **Gitee fork**(打了 3 处补丁:`project.exec` → `providers.exec`、
  `Path` → `String`、`compileSdk` 33 → 36),`pubspec.yaml` 里钉死 commit sha。

## 一、版本概述

v1.0.1 让应用"能听会说",但**每轮对话都是失忆的**:只有最近 20 条消息进提示词,超出即遗忘;
用户自己的资料无从进入模型视野。

v1.0.2 补的是**记忆与知识**这一层 —— 三块能力:

| # | 增量 | 一句话 |
|---|---|---|
| 1 | **本地知识库(KB)** | 导入 txt/md 文档 → 本地切块 + 本地向量化 → 对话时检索并注入 |
| 2 | **本地短期记忆(STM)** | 当前会话的工作记忆:最近若干轮原文 + 更早轮次的**滚动增量摘要** |
| 3 | **本地长期记忆(LTM)** | 跨会话的持久事实,按说话人隔离,自动抽取、检索注入 |

一句话边界:**向量计算完全离线**(本地 ONNX 嵌入模型),**记忆抽取与回答生成用在线 LLM**。
即"检索离线、生成与提炼在线"。

> ⚠️ 本版引入的是**至今最重的一块新依赖**(第二个 ONNX Runtime 副本 + 23MB 嵌入模型),
> 见[第十一节 实施阶段](#十一实施阶段接续现有阶段-11)与[第十二节 风险与坑](#十二风险与坑实施必读)。
> 这是本版最大的成本项。

### 1.1 与已有能力的关系(避免重复造)

```
                  ┌─────────────────────────────────────┐
   conversation_messages (SQLite, v1.0.1 已有)           │
        │ 最近 20 条原文 ────────────────────────────────┐│
        │                                               ││
        └─ 超出窗口的旧轮次 ──► [STM] 滚动摘要 ──────────┤│
                                                       ││
   memories (新) ──► [LTM] 按说话人过滤 + 向量 top-k ────┤│
                                                       ││
   kb_chunks (新) ──► [KB] 全局向量 top-k ──────────────┤│
                                                       ▼▼
                                          [ContextAssembler] 预算编排
                                                       │
                                                       ▼
                                              LlmMessage[] → LLM
```

**关键区分**(三者不可互相替代):

| 能力 | 回答的问题 | 归属 | 生命周期 | 注入方式 |
|---|---|---|---|---|
| STM | "这场对话刚才说到哪了?" | 会话 | 会话结束即失效 | 顺序注入,不检索 |
| LTM | "关于这个人,我知道什么事实?" | **说话人** | 永久,可删 | **按说话人过滤** + 向量 top-k |
| KB | "用户喂给我的资料里怎么写的?" | 全局 | 永久,可删 | 向量 top-k |

> **STM 不是新的消息存储**。原文仍只存在 `conversation_messages`;STM 是它的**上层压缩视图**
> (摘要 + 摘要水位线)。造第二份消息表 = 两处真相,必错。

## 二、概念边界:三个"记忆"到底指什么

设计里最容易被含糊过去的就是这三个词。本版定义如下,**写进代码注释与 README**:

- **短期记忆(STM)** = 当前会话的工作记忆。包含两部分:① **最近 N 轮原文**(v1.0.1 已有,
  `_llmContextLimit = 20`);② **更早轮次的滚动摘要**(本版新增)。STM 的增量只是② ——
  如果没有②,长对话会"忘了开头",而这不是靠加窗口能解决的(窗口拉满会挤掉知识库与记忆的预算)。
- **长期记忆(LTM)** = **关于某个人的、跨会话成立的短事实**。例:"张三偏好简洁回答"、
  "张三在做 Flutter 语音项目"、"张三月末要去北京出差"。**不是**对话原文,是提炼后的结论。
  必须挂说话人 —— 这是本版与 v1.0.1 声纹能力的直接咬合点。
- **知识库(KB)** = **用户主动导入的文档**。与 LTM 的本质差别:**KB 是用户显式提供的资料,
  LTM 是从对话里推断出来的事实**。两者混在一张表里会导致"我明明没导入过这个"的困惑,
  也会让"删除某人记忆"顺手删掉知识库(或反之)。**分开存、分开删。**

## 三、技术栈新增

| 组件 | 方案 | 已核实的事实 |
|---|---|---|
| 文本向量化 | `flutter_onnxruntime` **^1.8.5** | 见 3.1 |
| 嵌入模型 | `Xenova/bge-small-zh-v1.5` 的 `onnx/model_quantized.onnx`(int8) | **24,010,842 B**;512 维 |
| 中文 BERT 分词 | **自实现**(纯 Dart,读 `tokenizer.json`) | `tokenizer.json` 439,125 B / `vocab.txt` 109,540 B |

### 3.1 为什么是 `flutter_onnxruntime` 而不是 `onnxruntime`

**已核实的排除理由**:`onnxruntime`(gtbluesky,最新 **1.4.1**)有**未修复的 Android
`libonnxruntime.so` dlopen 失败**(issue #28,2024-12 报出、2025-11 仍无解决)以及
`MergeNativeLibsTask` 重复库报错。**不要选它。**

`flutter_onnxruntime`(masicai,最新 **1.8.5**,2026-09-08 发布,2026 年持续维护):
- ONNX Runtime **1.23.0**;**≥1.5.1 才满足 16KB 页面对齐**(Google Play 要求)
- 近期修过 ARM64 SME 设备 OOM、AGP 9 built-in Kotlin、iOS ITMS-90208
- **支持从文件路径建会话**(决定性的 API):
  `ort.createSession('/abs/path/model.onnx', options: OrtSessionOptions(intraOpNumThreads: 2, interOpNumThreads: 1, providers: [OrtProvider.CPU], useArena: true))`
- Android 需 `android/app/proguard-rules.pro`:`-keep class ai.onnxruntime.** { *; }`

> ⚠️ **本引擎不需要后台 isolate**(与 sherpa 铁律不同)。它是 **method channel 插件**,
> 推理在原生侧执行,Dart UI isolate 本就不被阻塞。但**接口形状照抄现有引擎**
> (抽象 + 可注入假实现),否则测试没法 faking。

### 3.2 嵌入模型的下载源:用 ModelScope,不用 hf-mirror

**已核实的下载源对比**(2026-09-29 实测):

| 源 | 结果 |
|---|---|
| `huggingface.co` 直连 | ❌ **无响应(被墙)** |
| `hf-mirror.com` | ✅ 302→200,`model.onnx` = 94,851,877 B |
| **`modelscope.cn`** | ✅ **推荐** —— 4 个文件全部 `HTTP 200` |

**选定的仓库:`Xenova/bge-small-zh-v1.5`(ModelScope 上存在,与 HF 同名同内容)**

| 文件 | 远端路径 | 字节 |
|---|---|---|
| 模型(单文件,int8) | `onnx/model_quantized.onnx` | **24,010,842** |
| 分词器 | `tokenizer.json` | 439,125 |
| 词表 | `vocab.txt` | 109,540 |
| 配置 | `config.json` | 716 |

基址:`https://modelscope.cn/models/Xenova/bge-small-zh-v1.5/resolve/master`

**已实测的下载行为**(决定能否复用现有 `HttpModelDownloader`):
- `Range: bytes=0-1023` → **`HTTP/1.1 206 Partial Content`** ⇒ **断点续传可用**,现有
  dio Range 续传逻辑**零改动**即可复用。
- 取回前 16 字节 = `\b\006\022\r o n n x . q u a n t i z`(ONNX protobuf:`ir_version=6`,
  `producer_name="onnx.quantize"`)⇒ **是真模型文件,不是拦截页**。这类校验要进代码
  (照抄现有 bzip2 魔数校验的思路)。

#### ⚠️ 3.2.1 必须先排除的坑:ONNX **外置数据**格式

同一个模型在两个仓库里的**文件形状不同**:

| 仓库 | 形状 |
|---|---|
| `Xenova/bge-small-zh-v1.5` ✅ | **单文件** `model_quantized.onnx` = 24,010,842 B |
| `onnx-community/bge-small-zh-v1.5-ONNX` ❌ | **拆分**:`model_quantized.onnx` = **168,002 B**(仅图)+ `model_quantized.onnx_data` = **23,774,208 B**(权重) |

拆分格式下,ORT 要求 `.onnx_data` **与 `.onnx` 同名同目录**,否则**加载失败**。
更糟的是:若把 `.onnx_data` 当"多余文件"忽略,报错信息对用户不可读。
**本版一律用 `Xenova/...` 单文件版**,并在 resolver 里对 embedding 种类断言"不得出现 `_data` 伴生文件"。

### 3.3 模型目录结构改动

嵌入模型需要**一次下载多个文件**,而现有 `ModelDownloadFormat.rawFile` 只支持单文件
(`url` + `rawFileName`)。改法(**向后兼容,现有条目零改动**):

```dart
enum ModelKind { …, embedding }          // 新增

/// 多文件裸下载的一个成员。
class ModelRawFile {
  final String remotePath;   // 'onnx/model_quantized.onnx'
  final String fileName;     // 落盘名 'model_quantized.onnx'(扁平化)
  final int sizeBytes;
}
// TtsModel 新增:final List<ModelRawFile>? rawFiles;
// 非空时优先用它;为空则回落到 url + rawFileName(现有行为不变)。
```

- **扁平化落盘**:`models/<id>/` 下直接放 4 个文件(远端目录层级不带进本地)。
  单文件 ONNX 无伴生依赖,扁平化安全。
- `ResolvedModelPaths` 增 embedding 分支:`modelPath`(onnx)+ `tokenizerJsonPath` +
  `vocabPath`;`isComplete` = 三者齐 + onnx ≥ 1KB(照抄现有校验)。
- `ModelCatalog.byKind(embedding)` 返回该条目;`kDefaultEmbeddingModelId` 常量。
- 体积展示:`sizeLabel` 按 `rawFiles` 求和(24.5MB)。

## 四、向量化运行时

### 4.1 流水线

```
文本 → WordPiece 分词 → input_ids/attention_mask/token_type_ids ([1,L] int64)
     → OrtSession.run → last_hidden_state [1,L,512]
     → 取 [CLS](token 0) 的 512 维                          ← CLS 池化,非 mean
     → L2 归一化(单位向量 ⇒ 余弦相似度 = 点积)
     → Float32List(512) ⇒ Uint8List(2048 B) 存 SQLite BLOB
```

### 4.2 已核实的模型参数(全部来自仓库配置文件,非记忆)

| 参数 | 值 | 来源 |
|---|---|---|
| 嵌入维度 | **512** | `config.json` `hidden_size` / `1_Pooling` `word_embedding_dimension` |
| 最大长度 | **512**(含 `[CLS]`/`[SEP]`,内容 ≤ **510**) | `config.json` `max_position_embeddings` |
| 池化 | **`pooling_mode_cls_token: true`**,`mean_tokens: false` | `1_Pooling/config.json` |
| `tokenize_chinese_chars` | `true`(中文按字切) | `tokenizer_config.json` |
| 词表大小 | 21128 | `config.json` `vocab_size` |
| 层数 / 头数 | 4 层 / 8 头(BERT-small) | `config.json` |

> ⚠️ **4.2.1 池化必须是 CLS,不是 mean**。这是最典型的"不报错只变差"错误:用 mean 池化
> 一样能算出 512 维向量、一样能存能检索,只是**相似度排序整体劣化** —— 没有任何异常可看。
> 依据:`1_Pooling/config.json` 的 `pooling_mode_cls_token: true`。

> ⚠️ **4.2.2 `do_lower_case` 两份配置互相矛盾**(实测):
> `sentence_bert_config.json` = **`true`**,而 `tokenizer_config.json` = **`false`**。
> 取 **`false`**(与 BAAI 原始仓库、Xenova 导出、`onnx-community` 三方一致;
> `sentence_bert_config.json` 里那个值是 sentence-transformers 写的遗留默认)。
> 影响面仅限拉丁字母/数字大小写,对中文几乎无感 —— 但**照抄 config 就得抄对那一份**。
> 实施时用 4.5 的自测确认。

### 4.3 自实现 WordPiece 分词器(纯 Dart)

**为什么自己写**:`transformers` 生态没有可用的纯 Dart 包,而 BERT 分词逻辑很小且**完全确定**,
自实现比引依赖更可控、可测。读 `tokenizer.json`(HF tokenizers 格式)即可拿到词表与参数。

实现要点:
- **BasicTokenizer**:`tokenize_chinese_chars: true` ⇒ **CJK 字符逐字切开**(前后补空格);
  空白切分;标点切分;`strip_accents`;`do_lower_case: false` ⇒ **不小写**。
- **WordPiece**:贪心最长匹配;续接前缀 **`##`**;未命中回落 `[UNK]`;`max_input_chars_per_word` = 100。
- **拼装**:`[CLS] ids [SEP]`,超出则截断到 510 内容 token;**`attention_mask` 全 1**
  (单条 infer,不做 padding;批处理时 padding 到批内最长并置 0)。
- `token_type_ids` 全 0(`type_vocab_size` = 2 但 BERT-zh 单句不用第二类)。

**验收**:同一段文本的分词结果与 Python `transformers` 对照(取 5–10 条样本固化进单测)。
这是纯函数,单测性价比最高的一块。

### 4.4 引擎与批处理

```dart
// lib/utils/memory/embedding_engine.dart
abstract class EmbeddingEngine {
  bool get isLoaded;
  Future<void> load({required String modelPath, required String tokenizerJsonPath,
                     required String vocabPath, int threads = 2});
  /// 批量:一次前向跑多块(批内 padding),返回 L2 归一化后的单位向量。
  Future<List<Float32List>> embed(List<String> texts);
  Future<void> unload();          // 释放 OrtSession,回收 ~100MB
}
class OrtEmbeddingEngine implements EmbeddingEngine { … }
```

- **必须批处理**:`[B, L]` 一次前向。逐块调用会让 1000 块 = 1000 次前向,
  单块 512 token 在手机上约 50–200ms ⇒ **1–3 分钟**;批大小 8–16 可摊薄到几十秒。
- **懒加载 + 空闲卸载**:与现有"各引擎独立懒加载"一致。嵌入 session 常驻约 100MB,
  导入/检索结束后空闲 5 分钟 `unload()`。
- 线程数 `intraOpNumThreads: 2`(与 sherpa 引擎同档,避免和 ASR/TTS 抢核)。

### 4.5 必做的自测(防"静默变差")

入库前跑一次,写成单测/调试页:
- 同义句对("我明天去北京" / "明天我要去北京")余弦 **应 > 0.85**
- 异义句对("我明天去北京" / "这个函数返回一个列表")余弦 **应 < 0.5**
- 若同义句分数明显偏低 ⇒ 先查**池化是否 CLS**、再查**是否归一化**、最后查 `do_lower_case`。

## 五、向量存储与检索

### 5.1 存储:SQLite BLOB,不做 FTS

沿用**同一个数据库文件** `sherpa_tts/conversation.db`,把 `SqliteConversationStore` 的
`_version` 从 1 提升,并在 `_migrations` 里追加建表步骤(该文件已有版本化迁移骨架,
新增表**不动老数据**)。

```sql
CREATE TABLE kb_documents (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  title TEXT NOT NULL, source_path TEXT, imported_at INTEGER NOT NULL,
  char_count INTEGER NOT NULL, chunk_count INTEGER NOT NULL,
  embedded_count INTEGER NOT NULL DEFAULT 0     -- 已回填向量的块数
);
CREATE TABLE kb_chunks (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  doc_id INTEGER NOT NULL, seq INTEGER NOT NULL,
  text TEXT NOT NULL,
  embedding BLOB,                                -- 512×float32 = 2048 B,可空
  dim INTEGER, model_id TEXT                     -- 换模型后能识别旧向量不可用
);
CREATE INDEX idx_kb_chunks_doc ON kb_chunks(doc_id);
CREATE INDEX idx_kb_chunks_pending ON kb_chunks(embedding) WHERE embedding IS NULL;
```

- **`embedding` 可空是核心设计**,见 6.3 的异步回填。
- **`model_id` 不可省**:换嵌入模型后旧向量与新向量**不可比**(且维度相同、不报错 ——
  与 v1.0.1 两个声纹模型同类的静默错误)。检索只取 `model_id = 当前模型` 的块;
  不匹配的块按"未嵌入"处理并提示重建索引。
- **不用 SQLite FTS5**:Android 系统 SQLite 在 **minSdk 23 上不保证 FTS5** 可用;
  而本项目检索是**向量**而非关键词,引 FTS 只是徒增版本分支。

### 5.2 检索:内存暴力点积,不引向量库

```dart
// 1. 查询向量(已 L2 归一化)
// 2. 全量载入候选向量(单位向量 ⇒ 余弦 = 点积,省掉除法与开方)
for (每个候选块) {
  var s = 0.0;
  for (var i = 0; i < 512; i++) s += q[i] * d[i];
  keep top-k
}
// 3. 阈值过滤:score < kbScoreThreshold 一律丢弃
```

**为什么暴力就够**(这是设计取舍,不是偷懒):

| 规模 | 内存 | 单查询浮点乘加 | 实测量级 |
|---|---|---|---|
| 1,000 块 | 2 MB | 51 万 | **亚毫秒** |
| 10,000 块 | 20 MB | 512 万 | 数毫秒 |
| 50,000 块 | 100 MB | 2,560 万 | 数十毫秒 |

个人知识库在 1 万块以内,**暴力点积的延迟完全不可感知**;HNSW/IVF 这类 ANN 索引在这个
规模只会引入构建成本、内存开销与"近似召回漏掉正确块"的新失败模式。
**规模上限写进计划:超过 ~5 万块再考虑 ANN 或按文档分页检索。**

**不引 sqlite-vec / 向量数据库**:多一个原生依赖 + 构建风险,收益为零。

### 5.3 检索失败必须降级为"不注入"

嵌入模型没下载、加载失败、查询超时、向量为空 —— **一律返回空列表,继续对话**。
知识库是增强,不能让它的故障打断语音对话(与 v1.0.1 门禁拒绝语"不卡死对话"同一原则)。

## 六、知识库

### 6.1 导入(仅 txt/md,本版范围)

`file_picker` → `FilePicker.platform.pickFiles(type: FileType.custom, allowedExtensions: ['txt','md'])`
→ 读文本(UTF-8,BOM/GBK 兜底)→ 建 `kb_documents` 行 → 切块入库 → 触发异步嵌入回填。

- 走 Android SAF,**不需要存储权限**。
- 编码:UTF-8 为主;检测失败时尝试 GBK(中文 txt 常见),再失败则报可读错误。
- 单文件上限(如 5MB 字符数上限 20 万)防一次导入把手机算爆;超限提示分段导入。

### 6.2 切块:必须新写 `KbChunker`,**不得复用 `TextChunker`**

> ⚠️ **这是本版一个明确的反模式警告**。`lib/utils/text_chunker.dart` 服务于 **TTS**:
> 首句 `1+4+10` 词、后续整句 ≤20 词 —— 目标是**合成不卡顿、朗读自然**。
> 对**检索**而言这套策略是错的:块太碎 → 单块语义不完整、检索命中率低。

`KbChunker` 策略(检索导向):
1. 优先按 **markdown 标题 / 空行段落** 切(语义边界);
2. 单段超长(> 510 token)时按**句末标点**二次切,保证不截断句子;
3. 相邻块**重叠 ~15%**(防答案恰好跨在边界上);
4. 硬上限 **510 token**(BGE `max_position_embeddings` = 512 含 `[CLS]`/`[SEP]`)。

**验收**:切块后逐块断言 token 数 ≤ 510、无空块、重叠存在、原文可无损覆盖。

### 6.3 异步嵌入回填(本版一个关键取舍)

**导入是瞬时的,嵌入在后台补齐。** 顺序:

1. **同步**:文本落库,`kb_chunks.embedding = NULL`。用户立刻在列表里看到文档。
2. **后台**:按 `embedding IS NULL AND model_id = 当前模型` 批量取块(批 8–16)→
   一次前向 → 回填 `embedding`/`dim`/`model_id` → 更新 `kb_documents.embedded_count`。
3. **检索只取 `embedding IS NOT NULL`** 的块。未嵌入完的文档**部分可检索**,
   列表上显示"索引中 3/12"。
4. 任务**可取消**、可断点续(下次启动继续),进度经 `ChangeNotifier` 上报 UI。
5. 全文有进度:`document → 第 i/N 批`。

> 为什么不让用户干等:1000 块嵌入要几十秒到几分钟。让"导入"变成秒级操作,
> 把长任务变成可后台、可中断、可观察的状态,**比一个转圈对话框好得多**,也顺带解决了
> "导入中杀进程"的一致性问题。

### 6.4 知识库管理页

`lib/pages/knowledge/knowledge_page.dart`(push):
文档列表(标题 / 来源 / 块数 / 索引进度 / 大小)→ 导入按钮 → 删除单文档(连带删块)
→ 全部重建索引 → 检索试跑(输入一句话,看召回的片段与分数)。

**"检索试跑"必须有**:检索质量不可见时,用户与开发者都只能猜。这是本版最重要的调试入口。

## 七、短期记忆(STM)

### 7.1 会话分段

引入 `session_id`。规则:**`start()` 时若距上次活动 > 30 分钟(或用户点"新会话")则新建 session**。
`conversation_messages` 增 `session_id` 列(`ALTER TABLE ADD COLUMN`,老数据回填当前 session)。

> 为什么不用"清空历史"当边界:用户清空历史是**删数据**的语义,不该顺带切会话;
> 而"停了一会儿再聊"才是自然的会话边界。

### 7.2 滚动增量摘要

```sql
CREATE TABLE session_summaries (
  session_id TEXT PRIMARY KEY,
  summary TEXT NOT NULL,
  summarized_up_to_id INTEGER NOT NULL,   -- 水位线:已摘要到哪条消息
  updated_at INTEGER NOT NULL
);
```

**触发**:每轮结束后异步检查;当「该 session 中 `id > summarized_up_to_id` 的消息数 ≥ 10」
时,取最老的 10 条 **+ 已有摘要** → 调 LLM 产出**新摘要** → 更新水位线。

> ⚠️ **7.2.1 必须增量,不能全量重摘要**。全量重摘要是 O(n²) 的 token 消耗:
> 100 轮对话会让摘要花费爆炸式增长。水位线 + 增量追加是唯一可行形态。

> ⚠️ **7.2.2 摘要失败绝不能阻塞对话**。LLM 报错/无网/超时 → **静默跳过本轮**,
> 水位线不动,下轮再试。绝不能因为"总结失败"让用户说不下去话。

- 摘要提示词要求:**保留人物、决定、待办、情绪转折**;丢弃寒暄;限 200 字以内。
- 摘要本身也用**当前说话人**标注(多说话人共用一条时间线,摘要里要能看出是谁说的)。

### 7.3 降级

无 LLM 配置 / 离线 ⇒ STM 退化为"只有最近 20 条原文"(= v1.0.1 行为)。**不报错,不提示。**

## 八、长期记忆(LTM)

### 8.1 存储

```sql
CREATE TABLE memories (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  speaker TEXT NOT NULL,               -- 归属说话人(声纹名)
  kind TEXT NOT NULL,                  -- fact | preference | event | relation
  content TEXT NOT NULL,
  embedding BLOB, dim INTEGER, model_id TEXT,
  confidence REAL NOT NULL DEFAULT 0.7,
  source_msg_id INTEGER,               -- 可追溯:哪句话得出的
  created_at INTEGER NOT NULL, updated_at INTEGER NOT NULL
);
CREATE INDEX idx_memories_speaker ON memories(speaker);
```

### 8.2 抽取(纯 LLM)

- **时机**:每 **4 轮**(可设)或会话结束时**批量**抽取一次。
  > 单轮抽取的 token 成本高且上下文不足(一句话常常推不出稳定事实);批量更省也更准。
- **输入**:最近若干轮对话 + 该说话人**已有记忆 top-k**。
- **输出**:JSON 数组,每条 `{op: "ADD"|"UPDATE"|"NONE", id?, kind, content}`。
  `UPDATE` 带已有记忆 id(冲突合并),`NONE` 表示"已有记忆已覆盖"。
  > ⚠️ **8.2.1 不去重会无限膨胀且自相矛盾**。每次抽取把已有记忆一起喂给 LLM 让它判定
  > ADD/UPDATE/NONE,是唯一低成本可行的去重手段。没有这一步,三个月后记忆库里会有
  > 五条"用户在减肥"和三条互相冲突的"用户不吃辣/用户爱吃辣"。
- **归属**:抽取时把**当前说话人**告知 LLM,记忆挂到该说话人。
- **未知说话人不抽取**(见 8.4)。
- **置信度**:LLM 给出的 `confidence` 直接落库;低于 0.5 的**不注入**提示词。
- **JSON 解析必须容错**:LLM 会用 ```json 包裹、会加解释文字。要剥离围栏 + 取首个
  `[` 到最后一个 `]` + 逐条 try/catch,单条坏数据不能毁整批(照抄现有 SSE 解析的容错思路)。

### 8.3 注入

按**当前说话人**过滤 → 向量 top-k(默认 6)→ 过阈值 → 按 `confidence` 与时间排序注入。

### 8.4 未知说话人 = 零长期记忆(硬约束)

> ⚠️ 未知说话人**既不被抽取、也不被注入**任何 LTM。与 v1.0.1「访客模式」语义一致:
> 访客问"我喜欢吃什么"时,若把张三的记忆注进去,就是**跨人信息泄漏** ——
> 而且是听起来非常自然、极难察觉的那种。判据与门禁一样,要看**当前识别结果**,
> 不能看"库里有谁的记忆"。

### 8.5 成本与开关

记忆抽取会产生**额外 LLM token 消耗**(用户自付 API 费用)。设置页开关 `memoryEnabled`
(默认开)+ 一行说明;无 LLM 配置时自动静默跳过。

## 九、上下文编排器(本版核心)

`_buildLlmMessages()` 目前是**同步**且只做「系统提示 + 身份/备注 + 最近 20 条」。
v1.0.2 抽出独立组件 `ContextAssembler`,并改为**异步**(KB/LTM 检索要 await)。

### 9.1 分节与预算

```
总预算 B(默认 4000 token 估算)
├─ ① 系统提示(用户配置)           固定,不裁剪
├─ ② 身份 + 说话人备注             固定,不裁剪
├─ ③ 知识库片段 top-k              ≤ 1200
├─ ④ 长期记忆 top-k                ≤ 600
├─ ⑤ 会话摘要(STM)                ≤ 500
└─ ⑥ 最近 N 轮原文                 剩余,且至少保留最近 4 轮
```

**裁剪顺序(先砍离当下最远的):③ KB → ④ LTM → ⑤ 摘要 → ⑥ 最近 N 轮。**
理由:越靠近"此刻这句话"的信息越不可省;知识库是增强,先让位。

> ⚠️ **9.1.1 token 是估算,不是精确计数**。用启发式(中文 ~1 字/token、英文 ~4 字符/token,
> 即 `est ≈ chars / 1.6`)并**预留 20% 安全余量**。不为此引入 tokenizer 依赖 ——
> 预算只需要"不超太多",不需要精确。**这一点要写进代码注释**,否则后来者会以为它是准的。

### 9.2 注入格式(防幻觉 + 防朗读噪音)

```
【已知资料】以下内容来自用户的知识库,仅供回答参考。
若资料中没有答案,请明确说"我不知道",不要编造。
[1] 来源:《产品手册》
<片段>
[2] 来源:《会议纪要》
<片段>

【关于当前说话人"张三"的长期记忆】
- 偏好简洁回答
- 在做 Flutter 语音项目

【本次会话早前摘要】
- 用户先询问了模型下载失败的原因,已建议切换镜像源;随后讨论了知识库导入格式。
```

> ⚠️ **9.2.1 必须显式要求"不要念出引用标记"**。本应用的回复会被 **TTS 朗读**,
> 若模型回答"根据资料[1]……",用户会**听见"资料方括号一"**。这是语音场景独有的坑,
> 文本聊天里根本不会暴露。提示词里要直接写:回答中不要出现 `[1]` 这类标记与来源说明。

### 9.3 检索时机

`_handleSegment` / `sendText` 中,**在构建消息之前** `await` 检索(KB + LTM 可并发),
查到什么就注入什么。检索耗时(数毫秒~数十毫秒)远小于 LLM 首 token 延迟,可忽略。

> 注意:`_buildLlmMessages()` 变 async 会影响 `test/conversation_service_test.dart` 的
> 现有断言 —— 实施时先改签名再跑测试,不要等最后一并发现。

19. **APK 会同时存在两份 ONNX Runtime**:sherpa 静态链接自己的 ORT,新插件提供
    `libonnxruntime.so`。两者 `.so` 名不同、静态链接隐藏符号,**共存安全**,但**体积叠加**
    (~15–25MB/ABI)+ 嵌入模型 24MB。构建后用 APK Analyzer 确认没把 `.so` 打进错误 ABI。
20. **首次构建需要 Maven 仓库**:插件从 **Maven Central** 拉 ORT 原生库。国内网络若卡住,
    在 `android/build.gradle.kts` 配阿里云 Maven 镜像。**这是本版最可能卡住的第一步。**
21. Android 需 `android/app/proguard-rules.pro`:`-keep class ai.onnxruntime.** { *; }`。

**嵌入正确性(全是"不报错只变差"型)**

22. **池化用 CLS 不是 mean**(`1_Pooling/config.json` 已核实 `pooling_mode_cls_token: true`)。
23. **`do_lower_case` 两份配置矛盾**:`sentence_bert_config.json`=true vs
    `tokenizer_config.json`=false → 取 **false**(BAAI 原始值)。
24. **必须 L2 归一化**;不归一化时"点积当余弦"是错的,且**排序看起来还算合理**。
25. **ONNX 外置数据陷阱**:`onnx-community/...-ONNX` 是 `.onnx`(168KB)+ `.onnx_data`(23.8MB)
    拆分格式,只下前者必然加载失败。**用 `Xenova/bge-small-zh-v1.5` 单文件版**,并在 resolver
    断言 embedding 目录不出现 `_data` 伴生文件。
26. **换嵌入模型后旧向量必须废弃**(`model_id` 不匹配即视为未嵌入)。512 维 VS 512 维
    **混用不报错**,与 v1.0.1 两个声纹模型的坑 13 完全同构。
27. **超长必须截断到 510 token**(`max_position_embeddings` = 512,含 `[CLS]`/`[SEP]`)。
    超长会**报错或静默截断**,取决于导出方式,别赌。

**原生资源**

28. `OrtSession.close()` / `OrtValue.dispose()` **不在 Dart GC 管辖内**。批量循环里漏
    `dispose` 会稳定泄漏原生堆直至 OOM —— 且 Dart 侧内存曲线**看不出来**。批量循环写
    `try/finally`。
29. 嵌入引擎**空闲必须卸载**:session 常驻约 100MB,与 ASR/TTS/声纹常驻会叠加。
    沿用"各引擎独立懒加载"的既有原则,且 **`IndexedStack` 三个 Tab 常驻 ⇒
    嵌入引擎不得在页面 build 时加载**(照抄坑 9)。

**设计与语义**

30. **不得复用 `TextChunker` 做知识库切块**:它按 TTS 短语策略切,对检索是错的语义边界。
31. **未知说话人零 LTM 抽取 + 零注入**:否则是极难察觉的跨人信息泄漏。
32. **知识库/记忆的检索失败一律降级为不注入**,不能打断对话。
33. **提示词必须要求不要念出 `[1]` 这类引用标记** —— 回复会被 TTS 朗读,文本聊天里不会暴露。
34. **STM 摘要必须增量**(水位线),全量重摘要是 O(n²) token 消耗。
35. **摘要/抽取失败静默跳过**,绝不阻塞对话、绝不弹错。
36. **`_buildLlmMessages()` 改 async** 会波及现有对话测试,先改签名再跑测试。
37. **导入的体积与算力上限**:单文件上限 + 批大小上限,防一次导入把手机算爆。
38. **知识库与长期记忆分开存**(表、删除入口都分开),合并会导致"删记忆顺带删资料"。
39. **编码兜底**:UTF-8 为主,失败试 GBK(中文 txt 常见),再失败给可读错误。

## 十三、验证

### 13.1 自动化

- **单元**:分词器对照 Python;切块边界(≤510 token/无空块/有重叠);`KbChunker` vs
  `TextChunker` 不互用;向量编解码往返;top-k 与阈值;`model_id` 不匹配视为未嵌入;
  嵌入回填可中断可续;抽取 JSON 容错(围栏/夹带/单条坏);ADD/UPDATE/NONE 去重;
  **未知说话人零注入**;预算裁剪顺序;KB/LTM 全故障降级;**STM 增量摘要的 LLM 调用次数
  随轮数线性增长**(防 O(n²) 回归);检索空结果不报错。
- **Widget**:知识库页(空态/索引中进度/导入失败);记忆管理页(列表/删除/清空);
  对话页"引用了 N 条资料"提示;"记住这条"。
- **Patrol**(已实施,见文首"实施完成度"):`knowledge_test.dart`(导入 → 假嵌入 →
  检索试跑命中)、`memory_test.dart`(对话抽取 → 分组管理)、`context_injection_test.dart`
  (KB/LTM/摘要注入提示词 + 未注册说话人零注入),复用 `test/support/fakes.dart` 与
  `buildPatrolTestDeps` 模式;全 fake 引擎,不依赖真实模型与网络。

### 13.2 真机全流程(必须跑)

1. **首次构建**:配好 Maven 镜像 → `flutter build apk --debug` 通过 → 确认 APK 内
   两份 ORT 与 ABI 正确。
2. **嵌入模型下载**:设置页点下载 → ModelScope 4 文件 → ready(**单独验证,这是新源**)。
3. **嵌入正确性**:检索试跑,同义句应高分、异义句应低分(= 4.5 自测真机版)。
4. **知识库全流程**:导入 1 个 md → 秒级入库 → 后台索引进度 → 检索试跑看召回 →
   对话提问,回答应引用到文档内容。
5. **重导入/重建索引**:换嵌入模型后旧文档索引重建,检索仍正确。
6. **STM**:连续对话 30+ 轮,确认**早期内容仍被记住**(摘要生效)且
   **没有重复总结**(水位线生效)。
7. **LTM**:注册张三 → 告知一个事实 → 后续对话确认已记住 → 杀进程重启后仍在 →
   **换未注册者提问,确认问不出张三的事**。
8. **降级**:删掉 LLM Key → 对话不崩、STM 静默降级、LTM 不抽取;
   删掉嵌入模型 → 知识库检索不注入但对话正常。
9. **成本可观察**:记录开/关记忆抽取时的 token 消耗差异(README 要写清这是用户自付)。

### 13.3 未验证项(规划时明确标注)

- ModelScope 在**应用内**(而非 curl)的下载稳定性与限速行为。
- `flutter_onnxruntime` 在 Android **真机**的推理速度(批大小 8–16 是否合理、是否发热)。
- 桌面(Windows 宿主)可用性 —— 该插件声明支持,但本项目历来"桌面未验证"。
- 嵌入质量对中文口语化查询(ASR 转写文本)的实际召回率 —— **需要真实语料实测**,
  `kbScoreThreshold` 的默认 0.45 是**猜测值,必须由实测校准**。

## 十四、安全与隐私边界

> ⚠️ 与 v1.0.1 的"声纹不是安全因子"并列的**第二条边界**,必须写进 README。

1. **知识库与长期记忆的内容会发给第三方 LLM**。本版把"送出去的数据"从"当前对话"
   扩大到"用户的文档片段与关于用户的持久事实"。**这是本版最大的隐私面变化。**
   提示词里注入的是**检索命中的片段**,不是整库 —— 但命中片段同样可能含敏感信息。
2. **知识库与记忆是明文落盘**(SQLite,非加密)。本机可读。与声纹嵌入同样的现状。
3. **记忆抽取会额外消耗用户自付的 API token**,且**每次抽取都会把已有记忆 top-k 一起发送**。
   开关默认开,但必须在设置页说明。
4. **未知说话人不注入任何长期记忆**(8.4)—— 这是本版唯一一条真正的隔离保证,
   必须有回归测试守住。
5. Phase 2 候选:知识库/记忆加密存储(与声纹嵌入搬 `flutter_secure_storage` 同一工单);
   导入文档的"不外发"标记(纯本地检索、不注入 LLM)。
